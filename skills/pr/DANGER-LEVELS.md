# 合并风险评估指南

此文档帮助准确评估 PR 的合并风险级别。

---

## 门类型判断

### 双向门（Two-Way Door）

**定义：** 可以轻松回退的变更。如果出问题，可以快速撤销。

**特征：**
- 不涉及数据持久化
- 不影响已发布的公共 API
- 可以通过代码回滚完全恢复
- 不需要数据迁移
- 影响范围可控

**典型场景：**

✅ **纯新增功能（不修改现有代码）**
```
新增一个独立的工具函数
新增一个新的 UI 组件
新增一个新的 API 端点（不影响现有端点）
```

✅ **UI/样式调整**
```
修改组件样式
调整布局
更新颜色主题
```

✅ **内部重构（行为不变）**
```
提取公共函数
重命名内部变量
优化算法实现（输出一致）
```

✅ **配置变更（非破坏性）**
```
添加新的配置项
调整默认值（向后兼容）
新增环境变量
```

✅ **日志/监控/文档**
```
添加日志输出
更新文档
添加性能监控
```

✅ **Feature Flag 控制的功能**
```
默认关闭的新功能
可以通过配置立即禁用的特性
```

---

### 单向门（One-Way Door）

**定义：** 难以或无法回退的变更。一旦合并，回退成本高或不可能。

**特征：**
- 涉及数据持久化或迁移
- 修改/删除公共 API
- 破坏向后兼容性
- 需要协调多个系统
- 回滚需要停机或数据恢复

**典型场景：**

🔴 **数据库 Schema 变更**
```sql
ALTER TABLE users DROP COLUMN old_field;
ALTER TABLE orders MODIFY status VARCHAR(20);
CREATE TABLE new_entity (...);
```
**为什么：** 数据已修改/迁移，回滚需要数据恢复

🔴 **破坏性 API 变更**
```
删除已发布的 API 端点
修改 API 响应格式
修改 API 参数（非可选）
重命名公共方法/类
```
**为什么：** 外部依赖已更新，回滚会破坏客户端

🔴 **身份验证/授权逻辑**
```
修改登录流程
更改权限检查逻辑
修改 token 验证
```
**为什么：** 安全相关，影响所有用户，错误后果严重

🔴 **支付/金融逻辑**
```
修改订单计算逻辑
更改支付流程
调整退款规则
```
**为什么：** 涉及金钱，错误导致财务损失

🔴 **数据迁移脚本**
```python
# 不可逆的数据转换
for user in users:
    user.new_field = transform(user.old_field)
    del user.old_field
```
**为什么：** 原始数据已丢失

🔴 **第三方集成变更**
```
切换支付网关
更换邮件服务商
迁移云存储提供商
```
**为什么：** 涉及外部系统，回滚复杂

🔴 **依赖重大升级**
```
React 16 → 18（破坏性变更）
Node.js 14 → 20（API 变更）
数据库引擎升级
```
**为什么：** 底层变更，影响广泛

## 影响范围评估

### 局部（Isolated）

**定义：** 变更仅影响单一组件、模块或功能。

**判断标准：**
- 修改文件 < 3 个
- 仅在一个子目录内
- 不影响公共 API
- 测试隔离良好

**示例：**
```
修改单个工具函数
调整一个 UI 组件样式
修复特定页面的 bug
```

### 中等（Moderate）

**定义：** 影响一个子系统或相关的多个模块。

**判断标准：**
- 修改文件 3-10 个
- 跨多个模块但在同一子系统
- 可能影响内部 API
- 需要多个测试文件更新

**示例：**
```
重构整个认证模块
添加新的数据验证层
优化数据库查询层
```

### 广泛（Broad）

**定义：** 跨多个子系统，影响核心功能或关键路径。

**判断标准：**
- 修改文件 > 10 个
- 跨多个子系统
- 影响公共 API 或核心功能
- 需要大量测试更新

**示例：**
```
重构状态管理（影响所有组件）
修改核心数据模型
更新日志框架（全局使用）
```

### 全局（Global）

**定义：** 影响整个应用、所有用户或关键基础设施。

**判断标准：**
- 基础设施变更
- 影响所有用户的功能
- 核心依赖升级
- 需要协调部署

**示例：**
```
数据库引擎升级
切换 CDN 提供商
更新身份验证系统
重写前端框架
```

## 风险评估矩阵

| 门类型 | 影响范围 | 风险级别 | 建议 |
|--------|---------|---------|------|
| 双向门 | 局部 | 🟢 低 | 快速合并 |
| 双向门 | 中等 | 🟡 中低 | 正常审查 |
| 双向门 | 广泛 | 🟡 中 | 仔细审查，分阶段发布 |
| 双向门 | 全局 | 🟠 中高 | 严格审查，金丝雀发布 |
| 单向门 | 局部 | 🟡 中 | 准备回滚方案 |
| 单向门 | 中等 | 🟠 中高 | 详细测试，准备迁移计划 |
| 单向门 | 广泛 | 🔴 高 | 分阶段部署，停机窗口 |
| 单向门 | 全局 | 🔴 极高 | 充分测试，协调部署，24小时待命 |

---

## 风险缓解策略

### 对于双向门

1. **充分测试**
   - 单元测试覆盖
   - 集成测试
   - E2E 测试

2. **代码审查**
   - 至少一名审查者
   - 关注边界情况

3. **金丝雀发布**（中等及以上影响）
   - 5% → 25% → 100%
   - 监控关键指标

### 对于单向门

1. **详尽测试**
   - 所有上述测试
   - 手动测试关键路径
   - 压力测试（如适用）

2. **回滚计划**
   - 编写回滚脚本
   - 测试回滚流程
   - 准备数据恢复方案

3. **分阶段部署**
   - Feature flag 控制
   - 逐步迁移用户
   - 保留旧代码路径（过渡期）

4. **监控告警**
   - 关键指标监控
   - 异常告警
   - 24小时待命

5. **沟通协调**
   - 通知相关团队
   - 协调部署时间
   - 准备应急预案

## 实际案例

### 案例 1：添加缓存层

**变更：** 在数据访问层添加 Redis 缓存

**初步判断：**
- 门类型：双向门（可以禁用缓存）
- 影响范围：中等（影响所有数据查询）

**风险评估：** 🟡 中

**缓解措施：**
- Feature flag 控制缓存开关
- 金丝雀发布：10% → 50% → 100%
- 监控缓存命中率和响应时间
- 保留直接查询路径作为降级方案

### 案例 2：删除已废弃的 API

**变更：** 删除标记为 deprecated 的 API 端点

**初步判断：**
- 门类型：单向门（无法恢复已删除的端点）
- 影响范围：广泛（外部客户端可能依赖）

**风险评估：** 🔴 高

**缓解措施：**
- 提前 30 天通知所有客户端
- 检查日志确认无调用
- 保留端点返回 410 Gone（而非直接 404）
- 准备紧急恢复方案
- 部署后密切监控错误日志

### 案例 3：UI 组件重构

**变更：** 重构 Button 组件的内部实现

**初步判断：**
- 门类型：双向门（外部 API 不变）
- 影响范围：广泛（所有页面使用）

**风险评估：** 🟡 中

**缓解措施：**
- 视觉回归测试
- 在所有使用场景测试
- 渐进式发布（页面级）
- 保留旧组件作为降级方案

## 常见误判

### ❌ 错误判断：数据库添加字段是双向门

**实际：** 单向门

**原因：** 
- 即使是添加字段，回滚时需要删除字段
- 如果字段已有数据，删除会丢失数据
- 依赖此字段的代码需要协调回滚

### ❌ 错误判断：内部 API 修改是局部影响

**实际：** 可能是中等或广泛影响

**原因：**
- 需要检查所有调用点
- 内部 API 可能被多个模块使用
- 影响范围取决于实际使用情况

### ❌ 错误判断：添加日志是零风险

**实际：** 低风险，但非零

**原因：**
- 大量日志可能影响性能
- 敏感信息可能被记录
- 日志存储成本

## 评估检查清单

在 PR 中填写合并风险时，确认：

- [ ] 门类型判断基于是否可回滚，而非变更大小
- [ ] 影响范围基于实际影响的代码/用户范围
- [ ] 考虑了数据持久化的影响
- [ ] 考虑了向后兼容性
- [ ] 评估了外部依赖的影响
- [ ] 单向门变更有详细的风险说明
- [ ] 高风险变更有明确的缓解措施
- [ ] 风险评估诚实，不低估问题

---

**原则：宁可高估风险，不要低估风险。**

错误的低风险评估会导致生产事故；  
准确的高风险评估会得到适当的审查和部署策略。
