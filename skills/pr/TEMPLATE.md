# PR 模板

使用此模板快速生成符合 WEN 标准的 PR 摘要。

## 基础模板

```markdown
## 摘要

[选择最合适的可视化方式]

## 证据

- **修改前:** [失败状态/问题截图/测试失败]
  **修改后:** [成功状态/解决截图/测试通过]

## 合并风险

**门类型:** [单向门 或 双向门]

[可选：风险说明]

**影响范围:** [局部/中等/广泛/全局]

[可选：潜在影响说明]
```

## 场景模板

### 1. 新功能添加

```markdown
## 摘要

添加 [功能名称]：

[组件树或文件树]

核心逻辑：
\`\`\`text
[伪代码或调用树]
\`\`\`

## 证据

- **修改前:** 该功能不存在
  **修改后:** 
  - 功能正常工作（附截图）
  - 测试覆盖：[X]%
  - 相关测试：
    \`\`\`
    ✓ should [测试场景1]
    ✓ should [测试场景2]
    ✓ should [测试场景3]
    \`\`\`

## 合并风险

**门类型:** 双向门

纯新增功能，不影响现有代码路径。可以通过 feature flag 控制。

**影响范围:** 局部

仅在 [模块名] 中添加新代码，不修改现有功能。
```

### 2. Bug 修复

```markdown
## 摘要

修复 [Bug 描述]：

\`\`\`diff
[显示修复的代码变更]
\`\`\`

根本原因：[简要说明]

## 证据

- **修改前:** 
  \`\`\`
  ✗ [失败的测试或错误输出]
  \`\`\`
  
  **修改后:**
  \`\`\`
  ✓ [通过的测试]
  ✓ [回归测试]
  \`\`\`

## 合并风险

**门类型:** 双向门

修复逻辑错误，不改变 API 或数据结构。

**影响范围:** [局部/中等]

影响 [具体模块]，已添加回归测试防止复现。
```

### 3. 重构

```markdown
## 摘要

重构 [模块名] 以提升 [可维护性/性能/可测试性]：

**文件结构变更：**
\`\`\`diff
[文件树 diff]
\`\`\`

**关键改进：**
- [改进点1]
- [改进点2]
- [改进点3]

## 证据

- **修改前:**
  - [问题指标：如复杂度、性能数据]
  
  **修改后:**
  - [改进指标]
  - 所有现有测试通过：[X] 个测试
  - 行为保持不变（验证方式）

## 合并风险

**门类型:** 双向门

纯内部重构，不改变外部行为。所有现有测试验证兼容性。

**影响范围:** 中等

影响 [子系统]，但通过测试套件保证行为一致。
```

### 4. API 变更

```markdown
## 摘要

[添加/修改/删除] API 端点：

**端点：** \`[METHOD] /api/path\`

**变更：**
\`\`\`diff
[API 签名或响应格式的 diff]
\`\`\`

## 证据

- **修改前:** [旧 API 行为]
  **修改后:** [新 API 行为]
  
**测试覆盖：**
\`\`\`
✓ should handle [场景1]
✓ should validate [场景2]
✓ should return error for [场景3]
\`\`\`

**兼容性：**
- [向后兼容说明 或 破坏性变更说明]

## 合并风险

**门类型:** [单向门 - 如果是破坏性变更]

[破坏性变更的详细影响分析]

**影响范围:** 广泛

影响所有依赖此 API 的客户端/模块：
- [受影响系统1]
- [受影响系统2]

**迁移计划：**
- [如适用，描述迁移步骤]
```

### 5. 数据库变更

```markdown
## 摘要

数据库 schema 变更：

\`\`\`sql
[DDL 语句或 migration 脚本关键部分]
\`\`\`

**变更类型：** [添加字段/修改字段/添加表/删除表]

## 证据

- **修改前:** [旧 schema]
  **修改后:** [新 schema]
  
**迁移测试：**
- 已在测试数据库验证
- 回滚脚本已测试
- 数据完整性检查通过

## 合并风险

**门类型:** 单向门

数据库 schema 变更，需要协调部署。

**影响范围:** 全局

影响：
- 所有依赖此表/字段的查询
- 现有数据需迁移
- 需要停机窗口：[是/否]

**部署计划：**
1. [步骤1]
2. [步骤2]
3. [回滚方案]
```

### 6. 性能优化

```markdown
## 摘要

优化 [功能/查询/算法]：

**优化方案：**
\`\`\`diff
[关键代码变更]
\`\`\`

## 证据

**性能对比：**

| 指标 | 修改前 | 修改后 | 提升 |
|------|--------|--------|------|
| [指标1] | [数值] | [数值] | [百分比] |
| [指标2] | [数值] | [数值] | [百分比] |

**基准测试：**
\`\`\`
[benchmark 输出]
\`\`\`

## 合并风险

**门类型:** 双向门

性能优化，不改变功能行为。

**影响范围:** 局部

仅影响 [具体功能]，已验证功能正确性。
```

## 快速检查清单

生成 PR 前确认：

- [ ] 摘要清晰，30 秒内可理解
- [ ] 使用了合适的可视化（代码树/diff/图表）
- [ ] 提供了真实的 before/after 证据
- [ ] 门类型判断准确（单向/双向）
- [ ] 影响范围评估诚实
- [ ] 高风险变更有详细的风险说明
- [ ] 使用了 GLOSSARY.md 中的领域术语
- [ ] 所有测试通过
- [ ] 代码审查完成

## 反面案例（避免）

### ❌ 糟糕的摘要
```markdown
## 摘要
修复了一些 bug 和添加了新功能。更新了代码。
```
**问题：** 太模糊，看不出具体改了什么。

### ❌ 缺失证据
```markdown
## 证据
代码可以运行。
```
**问题：** 没有具体的测试结果或截图。

### ❌ 风险评估不准确
```markdown
## 合并风险
**门类型:** 双向门
只是改了一下数据库 schema。

**影响范围:** 局部
```
**问题：** 数据库 schema 变更是单向门，影响范围通常不是局部。

## 工具提示

### 生成可视化

**Mermaid 图表：**
```bash
# 在 PR 中直接使用 mermaid 代码块
# GitHub/GitLab 会自动渲染
```

**文件树：**
```bash
tree src/ -L 2 -I 'node_modules|dist'
```

**代码 diff：**
```bash
git diff main...feature-branch -- path/to/file
```

### 截图工具
- macOS: Cmd+Shift+4
- 标注工具: Skitch, Annotate
- 动图: Kap, Gifox

```bash

npm test > test-results.txt 2>&1
```
