# 回顾检查清单

此检查清单帮助系统地进行会话回顾，确保不遗漏重要的改进机会。

---

## 📋 回顾准备

在开始回顾前：

- [ ] 确定回顾范围（当前会话 / 特定时间段 / 特定任务）
- [ ] 收集相关日志和输出
- [ ] 准备好访问相关文件（AGENTS.md, CODING_STANDARDS.md 等）
- [ ] 了解会话的主要目标和成果

---

## 🔍 检查维度

### 1. 导航效率

**检查点：**

- [ ] 代理花费多长时间找到目标文件？
  - 1 分钟内：✅ 优秀
  - 1-3 分钟：🟡 可接受
  - 3+ 分钟：🔴 需要改进

- [ ] 是否有重复的文件搜索？
  - 同一信息搜索 2+ 次：🔴 问题

- [ ] 文件组织是否清晰？
  - 相关文件是否在同一目录？
  - 文件命名是否反映其功能？

- [ ] 是否存在隐藏依赖？
  - A 文件修改需要同时修改 B 文件，但不明显

**改进方向：**
- 在 AGENTS.md 添加导航指针
- 重构文件结构
- 添加 README 指向关键文件

---

### 2. 自动化检查

**检查点：**

- [ ] 仓库有 pre-commit hook 吗？
  - 有且工作：✅
  - 有但失效：🔴 立即修复
  - 没有：🔴 立即添加

- [ ] CI/CD 运行哪些检查？
  - [ ] Lint
  - [ ] Type check
  - [ ] Unit tests
  - [ ] Integration tests
  - [ ] E2E tests

- [ ] 代理犯的错误是否可以被自动检测？
  - 类型错误：TypeScript strict mode
  - 未使用的导入：ESLint
  - 代码风格：Prettier
  - 安全问题：npm audit / Snyk

- [ ] 现有检查是否全部通过？
  - 有静默失败的检查吗？

**改进方向：**
- 添加缺失的检查
- 修复失效的检查
- 集成到 pre-commit hook
- 添加 CI job

---

### 3. 编码标准

**检查点：**

- [ ] 审查代理是否捕获了所有问题？
  - 漏报：🔴 标准不足或不明确
  - 误报：🟡 标准过于严格

- [ ] 哪些问题是机械性的（可自动化）？
  - 如果可自动化：应该是 lint 规则，不是文档
  - 如果是判断调用：应该在 CODING_STANDARDS.md

- [ ] 代码风格是否一致？
  - 不一致的地方：添加规则或 lint

- [ ] 是否有禁用的 API/模式？
  - 如果有：添加 lint 禁止规则

**改进方向：**
- 将机械性规则转为 lint 规则
- 在 CODING_STANDARDS.md 记录判断标准
- 更新审查代理的 brief

---

### 4. 信息访问

**检查点：**

- [ ] 代理是否需要但无法访问的信息？
  - 日志输出
  - 第三方 API 响应
  - 数据库状态
  - 环境变量

- [ ] 信息查找成本高吗？
  - 需要运行命令才能看到的信息
  - 需要访问外部系统的信息

- [ ] 是否有过时的信息？
  - 文档与实际不符
  - 注释与代码不符

**改进方向：**
- Tee 日志到文件
- 添加只读访问
- 更新过时文档
- 删除误导性注释

---

### 5. 工具经济性

**检查点：**

- [ ] 有昂贵的工具调用吗？
  - 多次读取同一文件
  - 多次运行同一命令
  - 大量 grep 搜索

- [ ] 工具调用是否必要？
  - 信息已经在上下文中
  - 可以从其他地方推断

- [ ] 自定义工具是否高效？
  - 输出是否简洁
  - 是否有冗余信息

**改进方向：**
- 缓存重复查询
- 优化工具输出
- 添加快捷工具

---

### 6. 无操作指令

**检查点：**

- [ ] AGENTS.md 中有不改变行为的指令吗？
  - "写好代码"（模型默认行为）
  - "仔细检查"（模型默认行为）
  - 重复的指令

- [ ] CODING_STANDARDS.md 中有未执行的规则吗？
  - 从未在审查中提及
  - 与实际代码风格不符

- [ ] 是否有过时的指令？
  - 针对已删除功能的指令
  - 不再相关的约束

**改进方向：**
- 删除无操作指令
- 删除或更新过时指令
- 合并重复指令

---

### 7. 代理协作（WEN 特定）

**检查点：**

- [ ] Executor 的 brief 是否清晰？
  - Executor 是否理解任务？
  - 是否有来回澄清？

- [ ] Reviewer 是否有效？
  - 发现了真正的问题
  - 没有过多误报

- [ ] Verifier 是否充分？
  - 验证覆盖了关键路径
  - 测试是否充分

- [ ] 协作是否高效？
  - 有不必要的往返吗？
  - 信息是否被重复传递？

**改进方向：**
- 优化代理 brief 模板
- 更新协作协议
- 改进信息传递机制

---

### 8. 产品意图保真度（WEN 特定）

**检查点：**

- [ ] PRD/spec 是否被遵循？
  - 有未实现的需求吗？
  - 有超范围的实现吗？

- [ ] GLOSSARY.md 是否被使用？
  - 代码使用了统一术语
  - 变量名与 glossary 一致

- [ ] 是否有 "代码获胜" 的情况？
  - 实现偏离 spec 但未获授权
  - 静默更改产品行为

**改进方向：**
- 强化 PRD 权威性检查
- 更新 GLOSSARY.md
- 添加 spec 符合性验证

---

### 9. TDD 执行（WEN 特定）

**检查点：**

- [ ] 测试是否先于实现编写？
  - RED 阶段：测试失败
  - GREEN 阶段：测试通过
  - REFACTOR 阶段：优化

- [ ] 测试覆盖率是否达标？
  - 80%+ 覆盖率
  - 关键路径 100% 覆盖

- [ ] 测试质量如何？
  - 测试是否有意义
  - 是否有假阳性测试

**改进方向：**
- 强化 TDD 流程
- 添加覆盖率检查
- 提升测试质量标准

## 📊 评分矩阵

为每个维度评分（1-5）：

| 维度 | 分数 | 说明 |
|------|------|------|
| 导航效率 | [1-5] | 1=非常困难，5=非常流畅 |
| 自动化检查 | [1-5] | 1=无检查，5=全覆盖 |
| 编码标准 | [1-5] | 1=无标准，5=严格执行 |
| 信息访问 | [1-5] | 1=无法访问，5=完全可得 |
| 工具经济性 | [1-5] | 1=非常浪费，5=非常高效 |
| 无操作指令 | [1-5] | 1=很多冗余，5=简洁精准 |
| 代理协作 | [1-5] | 1=混乱，5=高效 |
| 产品保真 | [1-5] | 1=严重偏离，5=完全符合 |
| TDD 执行 | [1-5] | 1=未遵循，5=严格执行 |

**总分：** [总和/45]

**评级：**
- 40-45：优秀 ✅
- 30-39：良好 🟢
- 20-29：及格 🟡
- < 20：需要改进 🔴

---

## 🎯 改进优先级矩阵

| 成本/收益 | 高收益 | 中收益 | 低收益 |
|----------|--------|--------|--------|
| **低成本** | 🔴 立即执行 | 🟡 本周执行 | 🟢 有空时做 |
| **中成本** | 🟡 近期执行 | 🟢 计划中 | ⚪ 可选 |
| **高成本** | 🟢 评估后决定 | ⚪ 可选 | ❌ 暂不考虑 |

**成本估算：**
- 低：< 30 分钟
- 中：30 分钟 - 2 小时
- 高：> 2 小时

**收益估算：**
- 高：每次会话节省 10+ 分钟 或 避免严重问题
- 中：每次会话节省 3-10 分钟 或 改善体验
- 低：每次会话节省 < 3 分钟 或 边际改进

## 使用提示

1. **定期回顾**：每周或每个大任务后进行
2. **聚焦高影响**：优先解决高收益低成本的问题
3. **跟踪改进**：记录实施的改进及其效果
4. **持续优化**：回顾本身也应该被优化
5. **分享学习**：将有价值的发现记录到项目文档
